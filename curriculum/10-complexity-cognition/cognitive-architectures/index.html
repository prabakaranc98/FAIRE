    Cognitive Architectures¶

    TL;DR: Cognitive architectures are structured frameworks that combine symbolic reasoning, persistent memory, and perception into a unified agent loop — and the frontier question is how to wrap LLMs inside these structures to get reliable, stateful autonomy that pure next-token prediction cannot provide.

    What it is¶

    Consider a state-of-the-art language model asked to play a game of chess over a long conversation. It can write a brilliant essay on Nimzo-Indian theory, explain the strategic logic of pawn structure, and quote Kasparov. Then, three moves into an actual game, it hallucinates a piece position — not because it lacks chess knowledge, but because it has no persistent board state. Every token it generates is conditioned only on the context window, which is a flat, undifferentiated sequence of text. There is no separate register that says "the knight is on f3 and has been there since move two." This is the core problem that cognitive architectures exist to solve: decoupling raw generation from persistent, structured state tracking.

    A cognitive architecture is a theory of mind made executable. The term originates in cognitive science, where researchers like Allen Newell and John Anderson asked whether human cognition could be explained by a single, unified computational framework rather than a patchwork of task-specific models. The answer they built — systems like Soar and ACT-R — separated cognition into distinct functional components: a working memory that holds the current situation, a long-term declarative memory that stores facts, a procedural memory that stores condition-action rules (called productions), and a central executive that cycles through perceiving, matching rules, selecting actions, and updating state. The cycle is tight, explicit, and auditable in a way that a neural network's forward pass is not.

    The modern relevance of this framework is that LLMs are extraordinarily powerful pattern-matchers but structurally weak at the things classical architectures were designed for: maintaining consistent state across time, applying rules without exception, and detecting when their own knowledge is insufficient. The emerging consensus at frontier labs is that neither pure symbolic systems nor pure neural networks are adequate alone. The productive direction is hybrid: use the LLM as an intuitive, language-capable pattern recognizer that initializes and expands a symbolic rule base, while the symbolic layer handles state persistence, conflict resolution, and verifiable execution. This is not a new idea — it is the rediscovery of Newell's insight, now equipped with a vastly more capable sub-symbolic component.

    Why it matters at the frontier¶

    The practical stakes are high because the failure modes of pure LLM agents in production are well-documented and structurally predictable. An LLM agent without explicit working memory will contradict itself across a long session. Without a conflict-resolution mechanism, it will apply incompatible strategies simultaneously. Without a meta-cognitive monitor, it will not know when it does not know something — it will confabulate. These are not bugs to be patched with better prompting; they are consequences of the architecture. Research in 2025 has begun to formalize this gap: work analyzing cognitive foundations for reasoning identifies 28 distinct cognitive elements present in human problem-solving traces and shows that current LLMs reliably fail on meta-cognitive self-awareness, episodic memory retrieval, and compositional rule application — precisely the components that classical architectures were built to handle.

    At the lab level, the interest is driven by the agent deployment problem. Systems like Google's Gemini agents, Meta's tool-use frameworks, and OpenAI's operator-facing products all require that an LLM maintain coherent task state across dozens of tool calls, recover gracefully from failures, and know when to escalate to a human. Each of these requirements maps directly onto a classical cognitive architecture component. The frontier question is not whether to use cognitive architecture principles — it is how to make the symbolic and neural components learn from each other dynamically, so that the system improves its rule base from experience without requiring a human to write every production rule by hand. That is the open problem that makes this an active research area rather than a solved engineering problem.

    Core concepts¶

    • Working memory — a bounded, rapidly-accessible store holding the current situation representation; in classical systems this is a set of typed attribute-value pairs (called "working memory elements") that productions match against.
    • Production rules — condition-action pairs of the form IF \(\langle\text{pattern}\rangle\) THEN \(\langle\text{action}\rangle\); the entire behavioral repertoire of a classical cognitive architecture is encoded as a set of these rules.
    • Recognize-Act cycle — the fundamental execution loop: match all productions whose conditions are satisfied by working memory, select one via a conflict-resolution strategy, fire it to update working memory, repeat.
    • Chunking — Soar's mechanism for compiling a successful problem-solving episode into a new production rule, so that the same reasoning does not need to be redone from scratch; the architectural analog of learning from experience.
    • Impasse — a state in Soar where no production rule applies or multiple rules conflict irresolvably; the system responds by spawning a subgoal to resolve the impasse, which is where LLM integration is most natural.
    • Declarative vs. procedural memory — declarative memory stores retrievable facts (ACT-R's "chunks"); procedural memory stores executable rules; the distinction matters because LLMs conflate both into a single weight matrix, losing the separation that makes auditing possible.
    • Global workspace — Baars' theory, implemented in architectures like LIDA, where a "broadcast" mechanism makes a selected representation available to all specialized cognitive modules simultaneously, enabling coordinated behavior from modular components.
    • Meta-cognition — a system's capacity to monitor and regulate its own reasoning process; the component most consistently absent from current LLM deployments and most consistently present in human expert problem-solving traces.

    Mathematical foundations¶

    The production-system semantics can be stated precisely. Let \(W\) be the current working memory state, represented as a set of typed attribute-value triples. A production rule \(p_i\) is a pair \((C_i, A_i)\) where \(C_i\) is a conjunction of pattern-matching conditions and \(A_i\) is a set of working memory modifications.

    The conflict set at cycle \(t\) is:

    \[ \mathcal{K}(W_t) = \{ p_i \in P \mid C_i \subseteq W_t \} \]

    where \(P\) is the full production set, \(C_i \subseteq W_t\) means every condition in \(C_i\) is matched by some element of \(W_t\), and \(\mathcal{K}(W_t)\) is the set of all rules whose conditions are currently satisfied. This equation says that the conflict set is exactly the subset of productions that "fire-eligible" given the current world state — it is the architecture's perception of what it can do right now.

    The conflict resolution step selects a single rule to fire. In Soar, this is done by a preference system; in ACT-R, by utility maximization:

    \[ p^* = \arg\max_{p_i \in \mathcal{K}(W_t)} \left[ U(p_i) + \epsilon_i \right] \]

    where \(U(p_i)\) is the learned utility of production \(p_i\) (updated by reinforcement), and \(\epsilon_i \sim \mathcal{N}(0, \sigma^2)\) is a noise term that implements stochastic exploration. This equation says that the architecture selects the rule with the highest expected payoff, with noise to prevent deterministic lock-in on suboptimal rules.

    The working memory update after firing \(p^*\) is:

    \[ W_{t+1} = (W_t \setminus D^*) \cup A^* \]

    where \(D^*\) is the set of working memory elements deleted by \(p^*\) and \(A^*\) is the set of new elements asserted by \(p^*\). This equation says that firing a rule is a destructive update — the old state is partially erased and new facts are written in, making the cycle irreversible without an explicit undo mechanism.

    The chunking operation, which is the key learning mechanism, compiles a successful subgoal resolution into a new production. If the system resolved an impasse by executing a sequence of rules \((p_{i_1}, p_{i_2}, \ldots, p_{i_k})\) to produce result \(r\) from initial conditions \(C_\text{sub}\), chunking creates:

    \[ p_\text{new} = \left( C_\text{sub} \cap W_\text{top}, \; \{r\} \right) \]

    where \(C_\text{sub} \cap W_\text{top}\) is the intersection of the subgoal's triggering conditions with the top-level working memory elements that were relevant, and \(\{r\}\) is the result asserted back into the top-level context. This equation says that chunking abstracts away the intermediate steps and stores only the input-output mapping, making future recognition of the same situation instantaneous.

    Key algorithms / techniques¶

    • Soar (Laird et al., 1987; continuously updated) — a production-system architecture with universal subgoaling: whenever no rule applies, the system automatically creates a subgoal to resolve the impasse, and chunking compiles successful resolutions into new rules; the reference implementation for studying cognitive architecture dynamics.
    • ACT-R (Anderson et al., 1998) — a modular architecture with separate buffers for visual, motor, declarative, and procedural processing; each module has its own timing parameters fitted to human reaction-time data, making it the standard for cognitive modeling of human performance.
    • LIDA (Franklin et al., 2007) — implements Baars' Global Workspace Theory with a broadcast mechanism; a "codelets" model where many small agents compete for access to the global workspace, and the winner broadcasts its content to all other modules.
    • CogRec (2025) — a hybrid architecture where an LLM initializes a symbolic production rule base from natural language task descriptions and dynamically expands it by resolving impasses through LLM queries, then compiling the result into a new persistent Python rule; the first system to demonstrate LLM-driven chunking on open-domain tasks.
    • ReAct (Yao et al., 2022) — interleaves chain-of-thought reasoning traces with tool-use actions in a flat prompt loop; lacks persistent working memory but demonstrates that explicit reasoning steps before actions substantially reduce hallucination in tool-use settings.
    • Reflexion (Shinn et al., 2023) — adds a verbal self-reflection step after each episode, storing the reflection as a natural-language memory that conditions the next episode; a lightweight approximation of meta-cognition without a formal symbolic layer.
    • MemGPT (Packer et al., 2023) — implements a two-tier memory system (in-context "main memory" and external "archival memory") with explicit paging operations, giving an LLM agent the ability to manage its own context window as a virtual memory system.
    • Predictive Coding Architectures (Rao & Ballard, 1999; revived 2024–2025) — frame perception and action as joint inference in a hierarchical generative model where each layer predicts the layer below and updates on prediction error; recent work applies this to ground LLM representations in sensorimotor loops, reducing hallucination by anchoring generation to action consequences.

    Current SotA¶

    The strongest hybrid cognitive architecture results in 2024–2025 come from systems that use LLMs as rule initializers rather than as end-to-end reasoners. CogRec-style systems, which compile LLM-resolved impasses into persistent symbolic rules, outperform pure ReAct baselines on multi-step planning benchmarks by reducing repeated reasoning errors — the symbolic rule cache prevents the LLM from re-deriving the same conclusion incorrectly on a second pass. On the cognitive element taxonomy introduced in recent 2025 work, the best hybrid systems cover approximately 18 of 28 identified cognitive elements, compared to roughly 11 for pure LLM agents and 22 for human expert traces, with the remaining gap concentrated in meta-cognitive self-monitoring and episodic memory retrieval. Reflexion and MemGPT remain strong baselines for lightweight deployments where a full production-system backend is impractical, with MemGPT demonstrating coherent multi-session task continuity on document QA tasks that exceed the context window of any current model.

    What's happening now¶

    Research frontiers. The most active theoretical direction is formalizing the interface between neural and symbolic components. The question is not whether to combine them but how to specify the contract: what representation does the LLM hand to the symbolic layer, and what guarantees does the symbolic layer provide back? Work drawing on neuroscience (particularly predictive coding frameworks) argues that the interface should be action-grounded — the LLM's representations should be conditioned on the consequences of actions in the world, not just on text. This prevents the symbolic layer from receiving hallucinated inputs that it then faithfully executes, which is a failure mode observed in early ReAct deployments. Separately, the question of whether in-context learning constitutes genuine algorithmic learning (de Wynter, 2025) has direct implications for whether the LLM component of a hybrid system can be trusted to generalize its rule-expansion behavior to novel impasse types, or whether it is merely retrieving surface-similar patterns from pretraining.

    Engineering and systems. On the engineering side, the practical challenge is latency. A classical Soar recognize-act cycle runs in microseconds; an LLM API call runs in hundreds of milliseconds to seconds. Hybrid systems that call the LLM only on impasse (when no symbolic rule applies) achieve a reasonable amortized latency because most cycles are handled by the fast symbolic layer. The engineering pattern that is emerging in production systems is a two-tier dispatch: a local rule cache (implemented as a Python dictionary or a lightweight Datalog engine) handles the common case, and the LLM is invoked only when the cache misses. The compiled rule is then written back to the cache, so the LLM call cost is paid once per novel situation type. This is architecturally identical to Soar's chunking, implemented with modern tooling.

    Open problems. The central unsolved problem is dynamic rule compilation without human verification: given a natural-language description of a novel situation and an LLM-generated resolution, how can a hybrid system automatically verify that the compiled production rule is conflict-free with the existing rule base, does not introduce infinite loops, and is semantically correct — without requiring a human to inspect the rule? This is a formal verification problem over a dynamically growing rule set, and current approaches either require human-in-the-loop review (which breaks autonomy) or accept unverified rules (which introduces silent failures). A second open problem is the granularity of working memory elements: classical architectures use hand-designed ontologies, but hybrid systems need to auto-induce the right level of abstraction from natural language, and the wrong granularity causes either rule explosion (too fine) or loss of discriminative power (too coarse).

    In production¶

    • Google DeepMind — Gemini agent pipelines use structured tool-call graphs with explicit state tracking between calls, implementing a lightweight working memory over multi-turn sessions; described in the Gemini 1.5 technical report at deepmind.google/research.
    • Meta AI — the CICERO system for the game Diplomacy combined a language model for negotiation with a symbolic planning module (based on Picard) for strategic action selection, achieving human-level performance; described at ai.meta.com/research.
    • Microsoft Research — AutoGen implements a multi-agent conversation framework where each agent maintains its own context state and agents communicate via structured messages, approximating a distributed working memory across agent instances; documented at microsoft.com/en-us/research/project/autogen.
    • IBM Research — the Neuro-Symbolic AI toolkit integrates neural perception with symbolic reasoning engines (including a production-rule backend) for enterprise document processing, handling millions of documents per day with auditable rule traces; described at research.ibm.com/topics/neuro-symbolic-ai.

    Minimum Valuable Build¶

    What you're building: A "CogRec-lite" hybrid agent that maintains a symbolic Python rule cache, detects impasses when no rule matches a user query, calls the Gemini API to resolve the impasse, and compiles the solution into a new persistent production rule — demonstrating LLM-driven chunking in under 150 lines of code.

    Why this build: It makes the abstract architecture concrete: you will see the recognize-act cycle running, watch the rule cache grow from zero rules to a working knowledge base over a session, and observe the latency difference between a cache hit (microseconds) and an LLM call (seconds) — the core engineering tradeoff of hybrid cognitive systems.

    Stack: Python 3.10+, google-generativeai 0.5+, no GPU required, free-tier Gemini API key (15 requests/minute free as of 2025), runs on Google Colab CPU or any laptop.

    Estimated time: 45–60 minutes end-to-end, including API key setup.

    The recipe¶

    1. Install dependencies and configure the Gemini API key.
    # In a Colab cell or terminal
# pip install google-generativeai

import google.generativeai as genai
import re, json, time

# Set your free-tier API key from https://aistudio.google.com/app/apikey
GEMINI_API_KEY = "YOUR_API_KEY_HERE"
genai.configure(api_key=GEMINI_API_KEY)
model = genai.GenerativeModel("gemini-1.5-flash")  # free-tier model
print("Gemini configured:", model.model_name)
    1. Define the working memory and the production rule store.
    # Working memory: a simple dict of attribute -> value pairs
working_memory = {}

# Production rule store: list of (condition_fn, action_fn, description) tuples
# condition_fn: takes working_memory dict, returns bool
# action_fn: takes working_memory dict, returns (response_str, updated_wm)
production_rules = []

def add_rule(condition_fn, action_fn, description: str):
    """Add a new production rule to the rule base."""
    production_rules.append((condition_fn, action_fn, description))
    print(f"[RULE COMPILED] {description}")

# Seed with two hand-written bootstrap rules
add_rule(
    condition_fn=lambda wm: wm.get("query_type") == "greeting",
    action_fn=lambda wm: ("Hello! I'm CogRec-lite. What can I help you with?", wm),
    description="Respond to greetings"
)

add_rule(
    condition_fn=lambda wm: wm.get("query_type") == "farewell",
    action_fn=lambda wm: ("Goodbye! Session state has been saved.", wm),
    description="Respond to farewells"
)

print(f"Rule base initialized with {len(production_rules)} rules.")
    1. Implement the perception step — classify the incoming query into working memory.
    def perceive(user_input: str) -> dict:
    """
    Classify the user input and update working memory.
    Uses simple keyword matching for speed; LLM fallback handled at impasse.
    """
    wm = {"raw_input": user_input, "query_type": None}

    lower = user_input.lower().strip()
    if any(w in lower for w in ["hello", "hi", "hey", "greetings"]):
        wm["query_type"] = "greeting"
    elif any(w in lower for w in ["bye", "goodbye", "farewell", "exit"]):
        wm["query_type"] = "farewell"
    elif any(w in lower for w in ["what is", "define", "explain"]):
        wm["query_type"] = "definition_request"
        # Extract the subject
        match = re.search(r"(?:what is|define|explain)\s+(.+)", lower)
        if match:
            wm["subject"] = match.group(1).strip()
    else:
        wm["query_type"] = "unknown"

    return wm

# Sanity check
test_wm = perceive("Hello there!")
assert test_wm["query_type"] == "greeting", f"Expected greeting, got {test_wm}"
print("Perception check passed:", test_wm)
    1. Implement the recognize-act cycle with impasse detection.
    def recognize_act(wm: dict) -> tuple[str, dict]:
    """
    Match working memory against all production rules.
    Returns (response, updated_wm).
    If no rule matches, returns (None, wm) to signal an impasse.
    """
    for condition_fn, action_fn, description in production_rules:
        try:
            if condition_fn(wm):
                print(f"[RULE FIRED] {description}")
                response, updated_wm = action_fn(wm)
                return response, updated_wm
        except Exception as e:
            print(f"[RULE ERROR] {description}: {e}")
            continue

    # No rule matched — impasse
    print(f"[IMPASSE] No rule matched for query_type='{wm.get('query_type')}', input='{wm.get('raw_input')}'")
    return None, wm
    1. Implement the LLM-based impasse resolver and rule compiler (the chunking step).
    CHUNKING_PROMPT = """
You are a cognitive architecture assistant. A symbolic rule-based agent has reached an impasse:
it cannot handle the following user query.

User query: {raw_input}
Detected query type: {query_type}
Working memory state: {wm_json}

Your task:
1. Generate a helpful, concise response to the user query (2-3 sentences max).
2. Generate a Python condition function body that would match this type of query in the future.
   The function receives a dict called `wm` with keys like 'query_type', 'raw_input', 'subject'.
   Return True if the rule should fire, False otherwise.
3. Generate a Python action function body that returns a (response_string, wm) tuple.

Respond in this exact JSON format:
{{
  "response": "...",
  "condition_code": "return wm.get('query_type') == '...'",
  "action_code": "return ('...', wm)",
  "rule_description": "..."
}}
"""

def resolve_impasse_and_chunk(wm: dict) -> str:
    """
    Call the LLM to resolve an impasse, then compile the solution into a new rule.
    Returns the LLM's response to the user.
    """
    prompt = CHUNKING_PROMPT.format(
        raw_input=wm.get("raw_input", ""),
        query_type=wm.get("query_type", "unknown"),
        wm_json=json.dumps({k: v for k, v in wm.items() if k != "raw_input"}, indent=2)
    )

    print("[LLM CALL] Resolving impasse via Gemini...")
    t0 = time.time()
    llm_response = model.generate_content(prompt)
    latency = time.time() - t0
    print(f"[LLM CALL] Completed in {latency:.2f}s")

    # Parse the JSON response
    raw_text = llm_response.text.strip()
    # Strip markdown code fences if present
    raw_text = re.sub(r"^```(?:json)?\n?", "", raw_text)
    raw_text = re.sub(r"\n?```$", "", raw_text)

    try:
        parsed = json.loads(raw_text)
    except json.JSONDecodeError as e:
        print(f"[PARSE ERROR] Could not parse LLM JSON: {e}")
        return f"I encountered an issue processing that. Raw response: {raw_text[:200]}"

    user_response = parsed.get("response", "I'm not sure how to handle that.")
    condition_code = parsed.get("condition_code", "return False")
    action_code = parsed.get("action_code", f"return ('{user_response}', wm)")
    rule_description = parsed.get("rule_description", "LLM-compiled rule")

    # Compile the new rule dynamically (the chunking step)
    try:
        condition_fn = eval(f"lambda wm: {condition_code}")
        action_fn = eval(f"lambda wm: {action_code}")
        add_rule(condition_fn, action_fn, f"[CHUNKED] {rule_description}")
    except Exception as e:
        print(f"[COMPILE ERROR] Could not compile rule: {e}")

    return user_response
    1. Assemble the full agent loop and run a demo session.
    def cogrec_lite_agent(user_input: str) -> str:
    """Full cognitive cycle: perceive → recognize-act → (impasse → chunk) → respond."""
    # Step 1: Perception — update working memory
    wm = perceive(user_input)

    # Step 2: Recognize-Act cycle
    response, updated_wm = recognize_act(wm)

    # Step 3: If impasse, call LLM and compile new rule
    if response is None:
        response = resolve_impasse_and_chunk(updated_wm)

    return response

# Demo session — run these in sequence to watch the rule base grow
print("=" * 60)
print("SESSION START")
print("=" * 60)

queries = [
    "Hello!",                                    # hits bootstrap rule (cache hit)
    "What is working memory?",                   # impasse → LLM → new rule compiled
    "What is chunking?",                         # likely impasse → LLM → new rule compiled
    "What is working memory?",                   # should now hit the compiled rule (cache hit)
    "Goodbye",                                   # hits bootstrap rule
]

for q in queries:
    print(f"\nUSER: {q}")
    response = cogrec_lite_agent(q)
    print(f"AGENT: {response}")
    print(f"[RULE BASE SIZE] {len(production_rules)} rules")
    time.sleep(1)  # respect free-tier rate limits

print("\n" + "=" * 60)
print("SESSION END")
print("=" * 60)
    1. Inspect the compiled rule base to verify chunking occurred.
    print("\n[COMPILED RULE BASE]")
for i, (cond_fn, action_fn, desc) in enumerate(production_rules):
    print(f"  Rule {i+1}: {desc}")

# Verify that the second "What is working memory?" query was faster
# (no LLM call) by checking that the rule base grew after the first call
assert len(production_rules) > 2, "No rules were compiled — check LLM response parsing"
print(f"\nVerification passed: {len(production_rules)} rules in base (started with 2)")

    The key observable: the rule base grows from 2 to 3+ rules during the session, and the second "What is working memory?" query fires a cached rule without an LLM call. The latency difference (milliseconds vs. ~1.5 seconds) is directly visible in the terminal output.

    Common failure modes¶

    • JSON parse error from LLM → The Gemini model sometimes wraps JSON in markdown code fences; the re.sub stripping in step 5 handles this, but if it fails, add print(raw_text) before parsing to inspect the raw response and adjust the regex.
    • eval() compile error on condition/action code → The LLM occasionally generates multi-line code or uses variables not in scope; add a try/except around the eval calls (already included) and fall back to a no-op rule that returns the user response without caching.
    • Rate limit error (429) on free tier → The time.sleep(1) between queries handles the 15 RPM limit; if running in a fast loop, increase to time.sleep(5).
    • Rule fires incorrectly on second query → The compiled condition code may be too broad (e.g., return True); inspect the compiled rule description and manually remove it from production_rules with production_rules.pop(-1) before re-running.
    • google.generativeai import error → Run pip install google-generativeai --upgrade and restart the Colab runtime; the package name changed from google-generativeai to google-generativeai in 0.5 but the import path is stable.

    Code & implementations¶

    • Soar cognitive architecture (official) — https://github.com/SoarGroup/Soar — the reference C++ implementation with Python bindings; includes the chunking and universal subgoaling mechanisms described in this page.
    • ACT-R Python port — https://github.com/jakdot/pyactr — a Python implementation of ACT-R with declarative and procedural memory modules; useful for running cognitive models without the original Lisp environment.
    • MemGPT — https://github.com/cpacker/MemGPT — the official implementation of the two-tier virtual memory system for LLM agents; demonstrates the paging architecture described in the Key algorithms section.
    • Reflexion — https://github.com/noahshinn/reflexion — official implementation of verbal self-reflection as a lightweight meta-cognitive loop; runnable on standard OpenAI API.
    • AutoGen (Microsoft Research) — https://github.com/microsoft/autogen — multi-agent conversation framework with per-agent state management; the closest production-ready approximation of distributed working memory.
    • LangGraph — https://github.com/langchain-ai/langgraph — graph-based agent orchestration with explicit state nodes; the engineering primitive most commonly used to implement recognize-act cycles in Python production systems.

    What comes next¶

    Understanding cognitive architectures makes the design choices in LLM agent frameworks legible — what looks like arbitrary engineering in LangGraph or AutoGen is often an implicit implementation of a classical cognitive architecture component.

    • Agent Systems — agent frameworks are the engineering layer where cognitive architecture principles are instantiated; understanding the theory makes the framework design choices non-arbitrary.
    • Knowledge Representation — the working memory element ontology and production rule syntax are instances of knowledge representation formalisms; the choice of representation determines what the architecture can and cannot express.
    • Reinforcement Learning — the utility learning in ACT-R's conflict resolution is a form of model-free RL; understanding RL makes the learning dynamics of production-system architectures precise.
